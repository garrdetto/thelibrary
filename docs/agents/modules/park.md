# Thrill Park and Thrill Park 2

Theme-park builder: shared simulation, renderers, rides and saves. Moved out of AGENTS.md so it loads only when this area is worked on; keep it current here, not in AGENTS.md.

- `src/server/routes/park.ts`: `/api/park` multiplayer tickets (prefix `park:`), ticket redeem, gzip-compressed saves, one per park in `park_saves_by_park` keyed by user and `parkId` (`src/server/park-saves.ts`, created on first use; the server reads the park from the save data). Saving, the 5-minute autosave and leaving all write that park's own save and never touch another park; a park leaves the account and the leaderboard only through `delete`. The one-time `one-save-per-park` migration (`park_migrations`) moved the old slot saves (`park_saves`) and older `park_scores` leaderboard rows across; both old tables are kept but no longer read, and per-map company-value leaderboards in `park_scores_by_park` (one row per named park, keyed by `parkId`; it and `park_scoreboard_resets` are created on first use, plus `shot_at`, migration 0012). After every save and autosave of a solo scored park, the HUD posts `score` with `companyValue` (park value + cash − loans), the park name and the save as `snapshot`, then renders a whole-park overview with `ParkRenderer.captureOverview` (owned land framed at midday, JPEG) and posts it as `shot`, stored in KV `park-shot/<parkId>` and served publicly at `?shot=<parkId>`. Parks carry `named`; the HUD blocks play with a naming dialog until the player names the park (the `park` command sets `named`). The board's View button opens `ParkShotDialog.tsx` with the screenshot for anyone, signed in or not; from the menu board it also offers "Walk around in 3D" (`?view=<scenario>&park=<parkId>` returns the snapshot, opened read-only through `ViewSession`). Below each map's Richest Parks table is the Million Dollar Dash: the quickest in-game time (`time.seconds`) to `MILLION_VALUE` ($1,000,000 park value, `parkValue`) with a `MILLION_RATING` (750) rating at the same moment. The sim records the first such moment once in `park.millionAt` (`checkMillionDash` in `sim.mjs`, run with the rating update; older saves are backfilled from complete monthly history by `millionFromHistory`, flagged `approx`), saves keep it, and the server reads it from the snapshot sent with `score` into `park_million_by_park` (one row per park, fastest time kept, created on first use, removed on `delete`). `reset-scores` clears both boards for the map. Admin `reset-scores`. The board is `src/components/park/ParkScoreboard.tsx`.
- `src/server/routes/park-rides.ts` + `src/server/park-rides.ts`: `/api/park-rides`, Thrill Park custom rides from the admin Ride Creator. D1 `park_custom_rides` (migration 0021, also created on first use): `id` `cr_<10 hex>`, `status` `draft`/`published`/`retired`, `spec` JSON (Zod `rideSpecSchema`: name, description, category, footprint `size` in squares, `height`, cost, upkeep, capacity, ride and load time, price, `stats`, `motion`, and `bake` settings so the editor can reopen it), `mesh_version`. KV `park-ride/<id>/mesh` (baked `.tpr`, `src/lib/park/rideMesh.ts`), `/thumb` (build-menu WebP) and `/source` (the original .glb, also a Meshy Retexture/Remesh source `{ rideId }`). GET (public) lists published and retired rides that have a mesh as catalog entries; `?drafts=1` (admin) returns full records; `?mesh=`, `?thumb=`, `?source=` serve files (immutable with `&v=<meshVersion>`; drafts only to the admin). POST (admin, multipart: `spec`, `status`, optional `id`, `mesh`, `thumb`, `source`, `sourceJob`) creates or updates; PATCH `{id, status}` moves draft → published and published ↔ retired (never back to draft); DELETE `{id}` removes drafts only. A published ride's footprint can't change.
- Thrill Park (`#park`, module id `park`): `server/park/` is the shared simulation (terrain, catalog, coaster track physics, commands, guest and staff AI, finances, snapshots; types in `index.d.mts`). `src/lib/park/` holds the dependency-free WebGL2 renderer (`gl.ts`: smooth-normal mesh builder with per-vertex materials (`materials.ts`) and baked AO, indexed 24-byte vertices, GGX lighting with ACES tonemap, fitted sun shadow map with rotated PCF, height fog, procedural ground and water shading; quality tiers `low`/`medium`/`high` in `quality.ts` (`?quality=`, HUD button; starts on `low`, the HUD pick is saved in `park/quality`; `captureOverview` always renders `high`); `models.ts`: guests built by `addPerson` with 8 walk frames plus idle, 8 looks and a near/far detail level, organic scenery; `renderer.ts`: blended terrain with ambient occlusion and shorelines, built in `CHUNK` (16×16-tile) pieces that re-mesh only when a tile within `CHUNK_MARGIN` of them changes, and coaster track meshes that rebuild only when the ground, paths, scenery or track under them change (`trackSiteKey`), so placing something never rebuilds the whole park, a shadow pass then the main pass via `drawWorld`), the local and online sessions (`session.ts`) and the saves client (`api.ts`). The guest cap (`spawnRate` in `sim.mjs`) is the smallest of 4 × (30 + rideScore·26 + stalls·8), owned land × `GUESTS_PER_OWNED_TILE` (0.7, counted by `ownedTileCount` in `land.mjs`, cached by `state.landVersion`) and `MAX_GUESTS` (6,400 per park); `p.spawn.limit` says which applies and `GuestCapacity.tsx` shows it. Level land levels the dragged area to the height of the corner the drag started from (`levelStartHeight`, the `terrain` command's `sx`/`sy`). Paths: dragging with any path type quick-draws a straight ground path; the coaster-style path builder (`src/lib/park/pathBuilder.ts` plans each piece) opens whenever a path type is picked: clicking a tile starts a run, and each section button (stairs/slope/flat, up or down) builds that piece onto the end, with a 50% opacity ghost of the next piece. Slopes rise `SLOPE_RISE` (0.5 m), half of `STAIR_RISE` (1 m). A raised path tile stores its high end and ramps down to its lower neighbour (`pathRamp` in `terrain.mjs`; footpaths, queues and boardwalks ramp at most one slope, stairs any height), so sloped pieces run straight and a climb never directly follows a descent. Path geometry (ramps, stepped stairs, deck fascia, railings, legs) is `src/lib/park/pathModels.ts`, shared by built paths and the ghost. Every path tile stores its placement number in `map.pathOrder` (set by the `path` command from the drag's start, saved like the other map arrays, 0 in older saves), and queue lines follow that order (`server/park/queues.mjs`: `queueLinks`, `queueStep`, `queueLayout`): `followLine` walks from the ride gate along the build order, so a line that weaves row on top of row keeps its rows, and the renderer rails every queue tile on both sides (one railing per shared edge, always, not only when raised), runs the two stripes the way the line runs with a right-angle bend where it switches lanes, and leaves openings only at the gate end and where the line meets the footpath (`line.entry`→`join`; an unfinished line opens straight ahead of its last-laid tile). Auto-finish is the `pathFinish` command (`exit`, `sloped`), which searches down to the ground or an existing path and builds nothing if it can't. A level boardwalk piece is a flat deck on the tile's highest corner (or just above water) plus whole half-metres, never ground-following: the builder plans it that way (`planBoardwalk`), holding the run's height on stilts where the ground falls away and stepping up where it rises, and checks every planned piece against the `path` command's side-neighbour step rule (`stepsTooHigh`) so the ghost shows any refusal first. Ride exits can use queue-line tiles: `exitLine` in `guests.mjs` follows them to the footpath and guests walk out along it (`exitRide`/`exitStep`); entrance `queueLine`s never route through exit-line tiles. The renderer puts an overhead sign (`queueSignModel`) where each entrance queue meets the footpath; exits have none. Land is bought one square (`buyLand`) or by dragging an area (`buyLandArea`, `landAreaPlan`, up to 32×32, only squares connected to the park), $500 each (`LAND_SQUARE_COST`) in every scenario and mode. Realism mode is a switch at the top of the park menu (`ParkGame.tsx`): it creates the park with `createPark(..., { realism: true })` (solo, and the `create` socket request's `realism` for co-op and versus), stored as `state.realism` and saved with the park. Realism parks can borrow up to `REALISM_MAX_LOAN` ($150,000), and every ride costs `REALISM_RIDE_COST` (5×) to build through `rideCostScale` in `server/park/realism.mjs`: flat and custom rides (`flat`), track ride stations (`coaster`) and every track piece (`validatePieceAt`), so previews, presets, refunds (`entityCost(entity, state)`) and park value follow the price paid. Wages, electricity, upkeep, fees and land are unchanged; the HUD scales the build-menu prices with `rideCostScale`. Off-screen guests are culled before instancing (`culling.ts`). Flat rides with `resize` in the catalog (Swimming Pool, Wave Pool) are placed by dragging a footprint (`flat` with `w`/`h`); the entity keeps `size`, and `flatSpec`/`rideFlatSpec` in `flatspec.mjs` give cost, upkeep, capacity and stats from the size and, for rides with `waves`, the `wave` setting (`WAVE_SETTINGS`, changed with `rideSet`). Use `rideFlatSpec` rather than `FLAT_RIDES[...]` for those numbers. The renderer caches flat ride models per kind, size and wave; the Wave Pool model is `src/lib/park/waterModels.ts`. The other water rides (category `water` in `FLAT_RIDES`) are drawn by `waterRideModel` in `src/lib/park/waterRides.ts`, which the renderer tries before `flatRideModel`; keep their tintable surfaces light so the ride color shows. Custom go-kart tracks hold four karts per station tile (`kartCount`, up to `KART_LIMIT` 40), waiting two abreast with a row every half tile (`kartRestS`, `kartLane` in `track.mjs`) and setting off side by side. The Grand Prix Kart Track (style `kartWide`, `wide: true`) runs half a square to the right of its piece line over two squares (`wideShift`, `pieceCells(..., wide)`, two station tiles per piece), four karts abreast (`kartLanes`, `kartLimit` 80) and has no hairpins. Track pieces store their slope grade `g` (`slopeRate`): pieces built now are steeper (coaster steep about 60°, go-kart slopes about 27°) and pieces without `g`, including the ready-made designs, keep the original angles; the loader (`deserializePark`) must keep `c` ±3 and `g`. Raised paths may cross over track and track may pass under raised paths (`PATH_DECK_CLEARANCE`). Queued guests walk the line tile by tile (`g.qs`, `updateQueuePositions`) and `board` waits for the front guest to reach the gate. Ready-made coasters with a `footprint` (plus `height` and `cost`, shown on the design cards) must close their own circuit inside that footprint with no auto-complete tail; `park.test.mjs` builds each one to check this, so recompute those fields if track physics or piece costs change. Suspended Looper stations start `INVERTED_STATION_LIFT` (7 half-metres) above the ground. The Grand Prix centre line is eased in `buildTrackPath` (`smoothCurve`: Gaussian smoothing of position, tangent and right vector, ends pinned) so turns and slopes blend. Coaster and go-kart track (not Suspended Looper) may go underground down to `TUNNEL_DEPTH` (12 m), never under water: `tunnelKind` marks each track tile in `trackCells` as `cover` (roof `TUNNEL_HEAD` + `TUNNEL_ROOF` under the lowest ground corner) or `open` (an uncut-to-sky cut, which cannot sit under a footpath or object and which paths cannot cross); the renderer leaves open tiles out of the terrain (`isTunnelHole`) and `src/lib/park/tunnels.ts` builds the concrete tube with ribs, roof strips and chasing wall lamps for the ride camera, plus each open cut's sloped floor, retaining walls, portal frame with lamps and cement border. Guest intensity rules live in `server/park/thrill.mjs`: `guestProfile` (kid, casual, or thrill seeker at `THRILL_SEEKER_SHARE`), `intensityLimit` (maxI plus `warm` plus the friends nudge from `state.thrillCrowds`), `warmUp` and `lovesRepeats`. Guests carry `type` and `warm`; older saves default to casual or kid. Ride comments come from `server/park/comments.mjs` (`COMMENT_POOLS`, `recordComment`, `rideComment`; lines are picked by a hash of guest, ride and time, never `Math.random`). The ride window's "What guests are saying" (`RideComments.tsx`) fetches them through `session.rideComments(id)`, which reads local state or sends the `ride-comments` socket request online. Hotels are entities of type `hotel` (`server/park/hotels.mjs`: `HOTELS` styles with custom footprints between `min` and `max` (up to `HOTEL_SIZE_LIMIT`) and floor ranges, `HOTEL_ADDONS` (building add-ons and revenue amenities priced per room by `addonCost`), `HOTEL_SERVICE` levels, `hotelSpec` for rooms/cost/guest bonus with a high-rise premium, `hotelNight` for one night's books (rooms, amenities, resort fee, staff, utilities, upkeep, amenity running), `updateHotels` each new day for occupancy, books, `condition` wear and the ledger keys `hotels`/`hotelAmenities`/`hotelStaff`/`hotelUpkeep`, `hotelSpawn` for guests leaving hotel doors, `resortHotels` for districts). They are placed with `hotel`, edited with `hotelSet` (also `rate`, `service`, `refurbish`) and resized in place with `hotelResize` (`hotelResizeCost`); the HUD's Resorts tab and hotel window are `ResortPanel.tsx`, and `src/lib/park/hotelModels.ts` builds each style's mesh from its size, floors, colors, roof and add-on. Hotels top out at `HOTEL_FLOOR_LIMIT` (10 floors) and grow wide instead (lots up to `HOTEL_SIZE_LIMIT` 32); saves only check the upper size bound (`hotelLoadFits`), so older, smaller hotels keep their lots and taller ones load capped at ten floors. Walk-in amenities (`AMENITY_VISITS` in `hotels.mjs`: pool, restaurant, spa, kids club, gift shop with `amenityCapacity`, `amenityOpen` (pool and kids club close after dark), per-visit prices set with `hotelSet` `priceOf`/`price`, free pool and kids club for residents): `chooseTarget` in `guests.mjs` sends guests to `hotel:<id>` (`amenityTarget`), `enterHotel` takes payment into `hotelAmenities`, hides them in state `amenity` and counts them in `hotel.using`, and `leaveHotel` applies the visit's `effects` and puts them back at the door. Residents (`guest.hotel`) leaving or out late walk back into their own hotel (`homeTarget`). Daily walk-in counts are `hotel.today`/`yesterday`. The model's front plaza (`hotelLayout`: pool deck, café terrace, kids' play area, chase lights, lobby door at the entrance) exports amenity `spots`, and the renderer (`drawHotelCrowds`, `hotelDoors`, `doorWalks`) draws guests swimming and dining there from `using` plus a few residents, and animates guests walking between the path and the lobby door Ride colors are slots from `server/park/palette.mjs` (main, chase lights, glow lights, then ride parts); `rideColors(ride, park)` resolves them from the ride's `colors`, its park `scheme` (three per park, edited with the `park` command's `scheme`), the legacy color fields and slot defaults. Models mark slot surfaces with tint weights 0.1–0.9 (`SLOT` in `src/lib/park/neon.ts`) and lights with the `neon` material, which glows brighter at night and chases by its sway channel; `rideNeon.ts` adds lights to every flat and water ride, the renderer adds track lights to coasters, and the ride window's `RideColors.tsx` shows every slot plus a combo list of presets and the park schemes, while the Park window's scheme editor changes the three schemes. Custom rides (admin-made, ids `cr_…`): `server/park/customRides.mjs` validates catalog entries (`customRideDef`, `sanitizeMotion`) and `registerCustomRides` adds them to `FLAT_RIDES` with a `custom` block (`id`, `motion`, `meshVersion`, `thumb`, `retired`); rides are never removed, built-ins can't be overwritten, and the `flat` command refuses retired ones (`buildableRide` hides them from the build menu). The browser registers them before any park opens (`ensureCustomRides` in `src/lib/park/customRides.ts`, called by `ParkGame.tsx`) and the multiplayer service fetches `<site>/api/park-rides` on connect and every minute. The renderer builds custom models from the baked mesh (`customRideModel`, a placeholder frame until it downloads) and animates the moving part with `motionMatrix` (`src/lib/park/rideMotion.ts`: `spin`, `swing`, `wheel`, `drop`, `bob` about `motion.pivot`; triangles whose centroid is at or above `motion.split` move). `motion.pieces` (up to `piecesMax` 6, `sanitizeMotion`) adds extra moving pieces on top of that (`src/lib/park/ridePieces.ts`): each piece picks triangles by a height band (`from`/`to`) and distance from the main pivot (`inner`/`outer`), later pieces claiming triangles from earlier ones, and splits them into separate copies (`split` `pieces`: connected clusters, or `sectors`: equal slices) by `splitPieces`; each copy gets its own pivot (`hang` top/centre/bottom) and moves by `type` (`spin`, `swing` (free pendulum that leans out with the main spin), `wobble`, `flip` (full loops at amount 1 that finish upright, else rocking), `bob`, `level` (cancels the carrier's tilt, like wheel gondolas)) with `stagger` and `alternate`, carried by the main moving part (`on` -1), the base (-2) or the nearest copy of an earlier piece. Copies are baked into the mesh: `.tpr` `TPR2` adds an instance table (part ids 2 + n; `TPR1` files still load), and `rideMatrices` composes every part's transform for the renderer and the editor stage. The editor's stage freezes in place on Pause, steps one frame at a time, restarts the cycle and plays at 0.25–2×; the Extra moving pieces panel is `src/components/park/rides/PiecesPanel.tsx`. `motion.rise` (up to `riseMax` 40 m) lifts the main moving part during the ride on top of any motion type (`riseHeight`; `mainLift` adds drop and bob). The optional generated base is the spec's `platform` (`sanitizePlatform`, Zod `platformSchema`, carried to parks as `custom.platform`): shape, size, height (the model is lifted onto it), tiers with inset, top/side/trim colours and trim band, steps on chosen sides, a railing, and a fixed or telescoping support column under the main pivot. `src/lib/park/ridePlatform.ts` builds it (`platformGeometry`, `assembleRide`, `stripPlatform` for re-editing a baked ride) and bakes it into the mesh as part 249 (fixed) and 250 + k (column sections, stretched by `columnMatrices` so a rising ride never floats); `partMatrices` returns every part's transform for the renderer and the editor stage. The server allows `platformTriangles` (6,000) on top of the model's triangle limit. The editor panel is `PlatformPanel.tsx`; changing the base height shifts the split, pivot and piece heights with the model. The editor lays its settings out in tabs (Fit, Motion, Base, Moving pieces, Details & price) beside a sticky stage, with fields wrapping into columns; the stage's Add menu adds a base or a moving piece and opens its tab, the pink pivot and blue split-height handles can be dragged on the stage, and pieces reorder by dragging their grip (`movePiece` keeps carriers earlier in the list) or duplicate. A piece can also be chosen by clicking the model (`picks`, up to `picksMax` 24 rest-pose points, Pick on model pauses at the loading pose): `pickedTriangles` keeps the connected parts under the clicks within the piece's band plus look-alike copies when `matching`, clicked parts on the same spoke are joined into one copy (`joinAlongSpokes`), and hang `clicked` puts each copy's pivot at the click (turned round the centre for copies that weren't clicked). Settings sit in two fixed columns (one below 560 px). Admin number fields use `src/components/admin/NumberInput.tsx`, which keeps typed text, applies valid in-range values as you type and clamps only on blur or Enter. `src/components/park/ParkGame.tsx` is the menu and lobby, and `ParkHud.tsx` is the in-game interface. - Thrill Park 2 (`#park2`, module id `park2`) is Thrill Park on a different engine: the same `server/park/` simulation, models (`models.ts`, `waterRides.ts`, `hotelModels.ts`, `pathModels.ts`, `rideNeon.ts`), `ParkRenderer` logic (animation, culling, previews, picking, captures), HUD, sessions, saves (`park_saves_by_park`) and leaderboard (`park_scores_by_park`), so a ride added to Thrill Park appears in both and parks move freely between them. Only the GPU backend differs: `ParkRenderer` draws through `RenderBackend` (`src/lib/park/backend.ts`), Thrill Park uses `Gl` and Thrill Park 2 uses `src/lib/park2/babylonBackend.ts` (Babylon.js 9.34.0, bundled, WebGPU with an automatic WebGL2 fallback, loaded with a dynamic import by `ParkGame` `edition={2}`; its shaders are written twice, GLSL and WGSL, in `babylonShaders.ts`, and must stay that way because Babylon's WebGPU engine fetches a GLSL compiler from a CDN otherwise), which adds sky lighting, cascaded soft shadows, lamp lights at night, MSAA, bloom on neon, SSAO on high (geometry-buffer mode) and render-scale adaptation. Its look scales with the quality tier through a shader `fx` level (sunset sky, stars, clouds, haze, sky reflections on water and glass, foliage flutter, richer lamps and neon), which render-scale adaptation lowers on slow devices. PlayCanvas is no longer used by Thrill Park 2 or Life Sim (Northwoods Angler and Kestrel County still need it). Never fork ride or rule code per edition. Thumbnail: `public/images/modules/park2.webp`.
- The Demo Derby is also a Thrill Park ride (`demoDerby` in `FLAT_RIDES`, category `other`, an 8 × 8 footprint: a 5 × 8 walled dirt pad and 3 × 8 roofed bleachers seating 200, capacity 200), drawn by `src/lib/park/derbyModel.ts` in both editions; its ride window links to the Demo Derby learning module, whose arena in turn stands inside a saved Thrill Park 2 park. The same saved park surrounds Short Track Showdown's Thrill Park Speedway (`modules-src/shorttrack/data/park.json`, see `docs/agents/modules/shorttrack.md`); both read it through `modules-src/demoderby/models/parkSceneryBuild.ts`, so a change to the park's models shows in both.
- `server/park/` is shared by browser and server in the same way: change park rules there, never in the UI, and redeploy the multiplayer service afterwards. Online parks are server-authoritative: clients replay structural commands in server order, and dynamic state arrives in snapshots. Keep commands free of randomness so the replay stays identical.
- Thrill Park is an original game. Keep its names, rides, scenarios and art original; do not copy assets, names or branding from commercial games.
