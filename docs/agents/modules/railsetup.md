# Straight Rail Setup Lab

Chassis setup and suspension-geometry module (module id `railsetup`, `modules-src/railsetup/`, page `/modules/railsetup.html`, catalog card in `src/lib/modules.ts` with `public/images/modules/railsetup.webp`). It is a web port of the owner's Windows app StraightRailSetupLab.exe (version 1): a Go launcher that served an embedded web page in an Edge window. The launcher (local server, keep-alive pings, self-update) is not ported; the page and its math are. Keep this file current when the module changes.

## Access and its own page

- Private module: `privateModuleIds` in `src/lib/module-layout.ts` keeps it in `hidden` for everyone (`normalizeModuleLayout` adds it back, so Module order can't show it). The `/api/module-layout` GET drops it from `hidden` for administrators and for people granted `module:railsetup` (People & permissions lists it among the hidden modules), so only they see it in the library.
- Its own page is the route `/railsetup` (`src/routes/railsetup.tsx`): a full-window iframe of `/modules/railsetup.html?page=1` with a small "Return to Homepage" tab fixed bottom left (`.standalone-home-tab` in `src/styles.css`). It needs no sign-in; anyone with the link can open it. `?page=1` adds `rs-page` to the module's root, which lifts `.stats` and pads `.wrap` clear of the tab. `standaloneModulePages` sends the library's nav entry and `#module-railsetup` links to that page instead of the in-site frame.

## Calculations (`sim/`, renderer-free and deterministic)

- `sim/kin.ts`: typed line-for-line port of the app's `kin.js`. Front double A-arm corner (`build`, `poseAt`, `poseH`, `angles`, `ics`, `rollCenter`, `antiDive`, `shockLen`, `selfTest`) and the rear solid axle on four links (`rearBuild`, `rearAdjust`, `rearSolve`, `rearPose`). `rearResidual` says how far a solved axle pose misses the link lengths; above 1e-6 the links can't reach that pose.
- `sim/hardpoints.ts`: the CAD mounting points (`CAD`, app frame: x forward, y left, z up, inches), `reseat` (puts each front tire on flat ground, as the app does), the front sway-bar end-link ball joint centers read from the model (`END_LINKS`, used by the bar-twist plot), and the Zod schema for hardpoint files (`parseHardpoints`).
- `sim/inputs.ts`: every setup input with the original element ids, ranges and defaults (`SETUP_INPUTS`, `DEFAULTS`). Heave, roll and steer are view controls (`POSE_INPUTS`, `Lab.heave`, `Lab.roll`, `Lab.steerDeg`) and are not saved with a setup, exactly as in the original. Front adjustments `ADJ0`, rear link moves `RADJ0`, slug sizes `SLUGS`.
- `sim/lab.ts`: class `Lab`, the app's setup model: wheel and tire geometry, scale weights, ride heights, the at-rest wedge solve (rounds, caster jacking from steer, bar preload, chassis twist), Advanced mode (`advSolve`: springs and tires set the ride heights and cross, written back into `hlf`, `hrf`, `hrr`, `cr`), the steady-state turn (`calc`: roll shared front and rear through the frame's twist stiffness, roll centers, jacking, banking, anti-dive and anti-squat, gapped bump springs, grip balance), coilover motion-ratio tables, steering rack, 3rd-link loads, the tables (`live`, `rearReport`, `partsRows`) and the plot series (`frontRollAll`, `steerAll`, `rearRollAll`, `rearHeaveAll`, `thirdAll`, `sweep`). `update()` re-solves after an input change and rebuilds the corners when a wheel input changed; `recompute()` after a geometry change. `warnings()` adds one message the original lacked: when the rear links can't reach the solved pose.
- `sim/files.ts`: setup file import (`parseSetupFile`) that accepts the original app's export (`{app, kind: 'setup', setup}`) and keeps only known input ids; `setupFile` writes the same shape (`app: 'RailSetupLab'`).

## Page (`index.html`, `ui/`)

- The markup, ids, copy and CSS are the original page's, with these changes: saved setups go to the account (note `#sv-where`), the "as modelled" caster note is computed (`#cas-base`; the original's fixed text was stale), the caster readout updates after the re-solve, fonts are bundled from `fonts/`, and there is an exit-full-screen button. Visible copy never uses game words.
- Phones (860 px and narrower, the `@media (max-width:860px)` block at the end of `styles.css`): the panel stacks under a 48vh 3D view, the Setup / Kinematics / Plots bar sticks to the top of the panel, and every section header is a full-width collapsible bar. `App.fold` opens only Move the car at first and works as an accordion there: opening a section closes the others in the same tab and scrolls it into view. Phone and desktop folding are remembered separately (`shutMobile`, `shut` in the view preferences); desktop keeps the original's behaviour (only Bump springs folded at first, any number open). Inputs are 16 px so phones don't zoom, and touch targets are at least 36 px. The catalog card has `mobile: true`.
- `ui/scene.ts` (`ChassisScene`) poses the 143 CAD parts by name every frame; part names come from the original model, with the rear end housing renamed `rear housing` (it carried a real manufacturer's name). Materials are matte (gloss rule) and light intensities are the original's times π for three.js physical lighting.
- `ui/app.ts` (`App`) ports the original's controller; `ui/plots.ts` its charts (five groups front and rear, dashed baseline = the setup last saved or loaded).
- Saving: signed in, setups (up to 100) and one custom hardpoints file are kept per account through `/api/railsetup` (`src/server/routes/railsetup.ts`, tables `railsetup_setups` and `railsetup_hardpoints`, migration `0052_railsetup.sql`; GET returns `{signedIn, setups, hardpoints}`, POST actions `save`, `delete`, `hardpoints`, `clear-hardpoints`, same-origin). Signed out, setups last until the page closes; export and import JSON files work either way. Only view preferences (help seen, folded sections) use localStorage.

## Test on track

- The Test on track buttons (Track section and the view bar, `#tt-open`, `#v-track`) open `ui/track-test.ts`: a full-page overlay with Short Track Showdown's track test (`/modules/shorttrack.html?lab=1&rad=<Corner radius>&bank=<Banking>`, see `docs/agents/modules/shorttrack.md`). The page says `rail-test-ready`; the Lab answers with `{type: 'rail-setup', vehicle, name}` (name: the Saved setups name field, else the loaded or saved setup, else "Current setup"). The overlay stays loaded while hidden; reopening sends the setup again only when it changed, and a new corner radius or banking reloads the page. `rail-test-close` (its Back to setup button or Escape) hides it.
- Test drive baseline: the Track section's Save as Test Drive Baseline saves the current setup under the name `Test Drive Baseline` (an ordinary saved setup, so it goes to the account when signed in and is picked up on load; Use default baseline removes it and goes back to the Lab defaults). `TrackTest.handling()` sends `vehicle.handling` with the setup: `railHandling` solves the Lab's grip balance (`bal`, front minus rear grip in use, %) at the three `HANDLING_PHASES` (entry 0.9 g with 0.45 g braking, center 1.15 g, exit 0.9 g with 0.3 g throttle, at the setup's banking) for the setup and the baseline, and `handlingDelta` is the difference (+ tighter, − looser). The track test turns it into grip taken off the fronts (tight) or rears (loose), so the baseline drives balanced at the limit (see `docs/agents/modules/shorttrack.md`).
- The site ribbon shows a Straight Rail tab next to Axiom Radar (`src/routes/index.tsx`) for administrators and anyone who can see the module (it isn't in their `hidden` list); it links to `/railsetup`.
- `sim/vehicle.ts` `railVehicle(lab, name)` turns the setup into plain SI numbers (`RailVehicle` in `shorttrack/next/sim/railCar.ts`): it copies the Lab with the same hardpoints, adjustments and rear link moves, zeroes Lateral g, Long g and Banking (view controls, not the car), re-solves at rest and reads the corner force tables (`force` from `calc`: spring, bump spring after its gap, motion-ratio table), `bumpTravel`, static corner loads, front bar (with preload slack), rear bar, frame twist, roll centres and jacking against roll (`frontRollAll`, `rearRollAll`, `rearPose().ratio`), anti-dive and anti-squat against travel, camber and toe (bump steer) curves, rear steer against roll and heave, rollouts, tire rate, brake share and the frame ride-height points (`PER`, now exported from `lab.ts`) plus a nose point 32 in ahead of the front axle and 0.75 in above the front frame. `tests/vehicle.test.ts` checks it.

## Model

`public/models/railsetup/chassis.glb` (2.5 MB, 316k triangles, 143 parts) is built by `pnpm assets` from `assets-src/models/railsetup/chassis.glb`, which `node modules-src/railsetup/tools/prepare-model.mjs <original car.glb> 0.04 0.001` makes from the 70 MB model inside the exe: renames the housing, strips trimesh's per-mesh extras, welds and simplifies (meshopt, error 0.001). The asset preset `chassis` keeps every part as its own named node (`instance: false` skips GPU instancing, which would merge the 52 identical ball joints the page finds by name).

## Tests

`modules-src/shorttrack/tests/railHandling.test.ts` covers the handling deltas, the grip trims and the test driver's reactions. `tests/vehicle.test.ts` covers the track test car: valid against the track page's schema, weights and scales carried over, view sliders kept out, and spring, bump spring, cross, stagger, ride height and bar changes reaching it.

`node scripts/railsetup-tests.mjs` (part of `pnpm test`). `tests/parity.test.ts` replays 24 cases recorded from the original app (`tests/fixtures/parity.json`, numbers only) and requires every output to match within 1e-6. Outputs the original itself could not solve (rear axle poses the links can't reach, where both versions return noise) are skipped, and such a case must raise the reach warning. `tests/rules.test.ts` covers inputs, setup and hardpoint files and basic load transfer. To re-record, extract the original app's `web/` folder from the exe (Go `embed.FS`) and run `node modules-src/railsetup/tools/capture-parity.mjs <web folder>` (Playwright with Edge).
