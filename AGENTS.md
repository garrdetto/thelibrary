# myWorkHelper

TanStack Start / React 19 site on Cloudflare Workers with four areas: a creative studio (AI chat, images, lyrics), an 8-ball/9-ball pool game, a racing game with two tracks, Thrill Park (an original 3D theme-park builder), and accounts/admin. Live multiplayer for pool, racing and Thrill Park runs on a separate Node service in `server/` (Railway). The initial route must render this product, never a starter demo.

## Repository layout

- `apps/platform/`: the website (TanStack Start Worker): `src/` (routes, shell, dashboards, admin, Worker API), `public/`, `migrations/`, `wrangler.jsonc`, `vite.config.ts`, `tsconfig.json`, and `build/module-assets.ts`.
- `games/<module>/`: one self-contained folder per learning module. React modules keep code in `src/` and are mounted by the platform; static modules keep their pages in `public/`.
- `packages/shared/`: code used by both the platform and modules: `src/components/` (sign-in form, lobby and presence, lap record board, admin record reset), `src/lib/` (module catalog, lobby network, cue design), `src/styles/styles.css` (all site styling and tokens), `src/webgl/gl.ts` (WebGL2 helpers), and `public/module-scores.js` (score client for static modules).
- `server/`: the Railway multiplayer service, including the engines shared with the browser (`racing-engine.mjs`, `park/`). It stays at the root because Railway builds it as its own service.
- Import aliases (in `apps/platform/tsconfig.json` and `vite.config.ts`): `@/` is `apps/platform/src/`, `@shared/` is `packages/shared/src/`, `@games/` is `games/`. Use relative imports inside one area and aliases across areas. Shared code must not import the platform or a game.
- Run every script from the repository root (`pnpm dev`, `pnpm build`, `pnpm run db:migrate`). Dependencies stay in the root `package.json`, and Vite runs with the repository root as its root, so `wrangler deploy` at the root finds the build.

### Learning modules
- Site-facing copy calls everything "Learning Modules" on a site named "the library" (always lowercase). Never use the words game(s), gaming or entertainment in visible text, titles or metadata.
- `packages/shared/src/lib/modules.ts`: module catalog (titles, subjects, thumbnails in `apps/platform/public/images/modules/`). `apps/platform/src/components/ModuleHub.tsx`: the homepage library.
- `games/<module>/public/*.html`: standalone modules (Sandlot Sluggers 3D, Sandlot Sluggers, BotWreck 3D, chess, checkers, 2048, Chopper Cave, Short Track Showdown) embedded in an iframe at `#module-<id>`. Each game folder's `public/` is served at `/modules/` by `apps/platform/build/module-assets.ts` (dev middleware and client build), so URLs stay `/modules/<file>`; two folders publishing the same file name fail the build. Folders: `sandlot-sluggers-3d`, `sandlot-sluggers`, `botwreck-3d`, `chess`, `checkers`, `2048`, `chopper-cave`, `short-track-showdown`, `maple-street`. Sandlot Sluggers 3D (`sandlot3d.html`) loads three.js r128 from cdnjs and its roster/batter-card art from `games/sandlot-sluggers-3d/public/sprites/`. Its 3D players (`class Rig`) are 6-ft athletes about 7.5 heads tall (rig units times `RIG_S`): a sculpted chest, pelvis and an abdomen skinned between them, and each arm and leg is one continuous `LimbTube` whose muscle profile (`armProfile`, `legProfile`) rounds through the elbow or knee, so joints stay closed in any pose; hands, fielder's glove and cleats are separate meshes. Customisation channels: `PLAYER_LOOK[i]` (skin, skinMap, hair, hairStyle short/buzz/long/curly/dreads/bald, facialHair none/stubble/mustache/goatee/beard, eyes, number, sleeves, build) and `UNIFORMS.you` / `UNIFORMS.cpu` (jersey, trim, letters, undershirt, pants, belt, socks, stirrups, cleats, cap, bill, helmet); at runtime `rig.setLook({...})` and `setUniform(team,{...})`, both also on `window.__ss`. Batters and runners wear helmets, fielders caps. Sculpted faces and PBR materials (`STD`, `SKIN`, `HAIR`, PMREM sky reflection) are unchanged; `games/sandlot-sluggers-3d/public/faces.png` is not drawn on the models. Field geometry is in world feet with the back point of home plate at the origin (the foul lines run from it); the pitch crosses the zone (`ZZ`, `ZC`, `ZH`) over the middle of the plate. When the user's team fields, the defense never throws on its own: the player clicks a base marker (or presses 1–4) and `userThrow` sends the ball. The HUD shows a ghost ball where the last pitch crossed and a compact release meter beside the zone. Online play in these uses PeerJS room codes, not the `server/` service.
- Maple Street (`games/maple-street/public/maplestreet.html`, module id `maplestreet`) is generated: edit the TypeScript in `games/maple-street/` (`src/` client, `shared/` rules, `colyseus-server/` optional Node room) and rebuild with `bun games/maple-street/build.mjs`. It loads three.js r172 (WebGPU with WebGL2 fallback), Rapier 0.14 compat, PeerJS and colyseus.js from unpkg via an import map. `shared/RoomLogic.ts` is the single authority (lot ownership, build validation incl. batched `builds` gestures, money, $50,000 loan cap, mowing pay, deliveries, shops, fuel, needs and home-item use). The default mode is one persistent shared world: `/api/maplestreet` (`apps/platform/src/server/routes/maplestreet.ts`, members by session, guests by a zod-checked key) upgrades to the Durable Object `MapleStreetWorld` (`apps/platform/src/server/maplestreet-world.ts`, binding `MAPLE_WORLD`), which runs `shared/WorldServer.ts` and saves to the D1 table `maplestreet_world`. The same logic also runs in the page for solo play (Local Offline Simulation, also the fallback when anything online fails), in the host's browser for PeerJS rooms (`tl-maplestreet-<code>`), in the lock-holding tab for same-device tabs, and in the optional Colyseus server. Town layout (lots, roads, downtown shops, gas station) is `shared/WorldLayout.ts`; starter houses `shared/Seed.ts`; simulated neighbors `shared/Npc.ts`; Sims-style build/buy tools `src/build/BuildController.ts` with the catalog in `shared/Catalog.ts` and models in `src/build/Furniture.ts`; downtown `src/world/Downtown.ts`; instanced grass `src/world/Grass.ts`; HUD and town map `src/game/Hud.ts` and `src/game/PlotMap.ts`. Vehicles are original designs; keep brand names and logos out. `games/maple-street/` is excluded from `apps/platform/tsconfig.json`. Details are in `games/maple-street/README.md`.
- `games/pool/src/` (`PoolTable.tsx`, `CueArtwork.tsx`, `pool-computer.ts`, `pool-effects.ts`): pool. The lobby, presence and invite network used site-wide (`PoolLobby.tsx`, `SitePresence.tsx`, `pool-network.ts`) and `cue-design.ts` are in `packages/shared/src/`.
- `games/racing/src/Racing.tsx`, `games/racing/src/racing.ts`, `server/racing-engine.mjs`: racing. Max Secure Circuit (`#racing`) and Oval Speedway (`#oval`) are separate modules; each mounts `Racing` with `fixedTrack`. Their page styling uses the `--lib-*` site tokens (scoped under `.racing-content`) and the module accent from `modules.ts`.
- Thrill Park (`#park`, module id `park`): `server/park/` is the shared simulation (terrain, catalog, coaster track physics, commands, guest and staff AI, finances, snapshots; types in `index.d.mts`). `games/thrill-park/src/lib/` holds the WebGL2 renderer built on the dependency-free `packages/shared/src/webgl/gl.ts` (`gl.ts`: smooth-normal mesh builder, sun shadow map with PCF, specular/fresnel lighting, procedural ground and water shading; `models.ts`: guests built by `addPerson` with 8 walk frames plus idle, 8 looks and a near/far detail level, organic scenery; `renderer.ts`: blended terrain with ambient occlusion and shorelines, a shadow pass then the main pass via `drawWorld`), the local and online sessions (`session.ts`) and the saves client (`api.ts`). `games/thrill-park/src/components/ParkGame.tsx` is the menu and lobby, and `ParkHud.tsx` is the in-game interface. Thumbnail: `apps/platform/public/images/modules/park.webp`.

### Site changes (admin asks Claude to change the site)
- `apps/platform/src/components/SiteChanges.tsx` is a chat with Claude. Each admin message becomes a row in D1 `site_changes` (migration 0009, also created on first use) and `/api/site-changes` (`apps/platform/src/server/routes/site-changes.ts`) starts `.github/workflows/site-change.yml` through the GitHub API (`workflow_dispatch` with `job_id` and `callback_url`).
- The workflow runs `.github/site-changes/run.mjs`: it fetches the job and earlier turns from `/api/site-changes?job=` (Bearer `SITE_CHANGES_SECRET`), runs Claude Code headless with the request, reports progress back, then builds (`pnpm build`), commits and pushes to `main` (auto-publish) or opens a pull request (review first). New migrations are applied when Cloudflare secrets exist. Runs are serialized with a concurrency group. Undo runs `git revert` on the change's commit.
- Credits: Anthropic has no API for a prepaid balance, so the admin enters the balance and the panel subtracts each run's reported `total_cost_usd`. With `ANTHROPIC_ADMIN_KEY` set, it also shows the organization's month-to-date spend from the Admin cost report (cached 5 minutes in `site_change_settings`).
- Worker secrets: `SITE_CHANGES_GITHUB_TOKEN` (fine-grained token, Actions read/write on the repo), `SITE_CHANGES_SECRET`, optional `ANTHROPIC_ADMIN_KEY`, optional `SITE_CHANGES_REPO` (default `garrdetto/thelibrary`). Repository secrets: `SITE_CHANGES_SECRET`, and `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`; optional `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` for migrations; optional repository variable `SITE_CHANGES_MODEL`.

### Multiplayer server (`server/`)
- `server/index.mjs`, `server/racing.mjs` and `server/park.mjs` verify players by redeeming tickets at `<site>/api/pool-account?action=redeem`, `<site>/api/racing?action=redeem` and `<site>/api/park?action=redeem`. `FRONTEND_ORIGIN` must list the site origin.

## Conventions

Use TypeScript, descriptive identifiers, React hooks, and type-only imports. Keep provider SDKs and database imports out of client modules. Server and database relative imports use `.js` extensions. Validate runtime input with Zod. Preserve the CSS token system, responsive layouts, reduced-motion support, keyboard accessibility, and loading, empty, and error states. Do not add inline comments unless requested. Prefer adding new modules over growing the already large files.

## Platform rules

- All AI runs server-side with the Gemini API key secret. Text uses `gemini-3-flash-preview`; images use `gemini-3.1-flash-image`. Never expose environment values or provider errors.
- Use D1 for structured records and KV for binary data. Never use local files, browser storage, or in-memory persistence for data that must persist.
- Schema changes go in a new numbered file in `apps/platform/migrations/` and are applied with `pnpm run db:migrate` (wrangler with `--config apps/platform/wrangler.jsonc`).
- Non-GET endpoints check same origin. Ticket redeem endpoints are server-to-server and skip it.

## Accounts and access

- Accounts are a username (3–20 letters, numbers, `_`, `-`, stored lowercase) and a password of 3 or more characters (up to 128), hashed with a per-user salt. Older accounts created with 3 digits keep working. No registration page, email or recovery: an unknown username creates the account; a known username with the wrong digits returns "Invalid password."
- Wrong passwords lock the username after 5 attempts (15 minutes, doubling each time up to 24 hours) and the network after 25. Each network can create 10 accounts per day.
- The administrator is `stoegbauer`, whose password is the `ADMIN_PASSWORD` secret . The admin can rename accounts, grant studio pages, reset a password (next sign-in sets the new password) and delete accounts.
- Studio pages (chat, image, lyrics) require a grant from the admin. Pool and Racing require sign-in for saved data.
- Pool appearance, cue overlay, racing paint, lobby sound, site theme, saved lyric styles and lyric corrections are stored per account. There is no creation library; creations are kept only so revisions and version history work. Never include `user_id` in API responses.

## Studio rules

- Never claim chat includes live browsing or personal document retrieval.
- New lyrics, fine-tunes (`revise`), full rewrites (`revamp`), and manual edits are distinct. Fine-tunes are surgical, accumulate in `tuning`, and keep untouched lines. Revamps rewrite every line with current settings and keep the topic. Every derived version stores `parent_id`.
- Saved lyric styles store the full song settings including `instructions`, the user's standing writing directions, which the model follows as preferences under the mandatory rules.
- Explicit mode (default on) allows profanity but never slurs against protected groups.
- Artist influence and custom genres are researched server-side and cached in `research`, which is never public.
- Prompt text and instructions are ideas only: lyrics copying 4–5 word runs are regenerated once, then rejected. The validator requires bracketed sections and forbids intro lyrics.
- Image downloads are re-encoded through canvas. Serve stored images only through the ownership-checked `/api/asset`.

## Games rules

- `server/racing-engine.mjs` is shared by browser and server. Any change to it, or to server lobby/race code, requires redeploying the multiplayer service; bump the `/version` string in `server/index.mjs` and note it in `server/README.md`.
- Keep single-player and multiplayer physics identical by changing the shared engine rather than duplicating logic in `Racing.tsx`.
- Lap records are stored per track and mode. Short Track Showdown (`games/short-track-showdown/public/shorttrack.html`) posts to `/api/racing` with track `shorttrack` (Showdown Bullring) `dells` (Dells Short Track) or `dirt` (Dells Dirt Oval, dirt handling; picked in the module menu via `?track=`) and modes `time-attack`, `race` (solo vs AI) and `multiplayer`; every completed lap by the signed-in driver is sent (every time attack lap, and every race lap until that driver takes the checkered flag), and boards list every lap, so one driver can hold several places. The truck body is the owner's race-truck model (lofted body, greenhouse, roll cage, fascia, bed wing), embedded in the module as `TM` and scaled to the physics size; liveries are conforming decal meshes on the sides, hood and roof. Race numbers come from `games/short-track-showdown/public/shorttrack-numbers.js` (20 Google Fonts digit subsets, 11 styles plus slant, size 60–150% with 125% default, fill/outline/accent colors) and sit on their own decals on the doors, roof and tailgate; `cleanLv` keeps older liveries and older peers working (`italic` becomes `block` plus slant). `packages/shared/src/components/LapRecordBoard.tsx` shows the all-time top 20 per mode (tabs) under each racing module page: Max Secure Circuit and Oval Speedway via `Racing.tsx`, Short Track Showdown under its iframe. `GET /api/racing?records` is public; the module posts `{type:'tl-lap',track}` to the parent after a saved lap so the board refreshes.
- `server/park/` is shared by browser and server in the same way: change park rules there, never in the UI, and redeploy the multiplayer service afterwards. Online parks are server-authoritative: clients replay structural commands in server order, and dynamic state arrives in snapshots. Keep commands free of randomness so the replay stays identical.
- Thrill Park is an original game. Keep its names, rides, scenarios and art original; do not copy assets, names or branding from commercial games.

## Development

Install with `pnpm install`; develop with `pnpm dev`. Pushes to `main` build and deploy automatically through Workers Builds.

- Chat: floating `GroupChat` component (src/components/GroupChat.tsx) polls `/api/group-chat` (D1 `chat_messages` + `chat_presence`, migrations 0002–0003). `thread` NULL = everyone; otherwise the sorted comma list of member usernames (private chat, up to 8). Presence (who's online) comes from these polls, not Railway. Read receipts: viewing a thread posts `{action:'read', thread, id}` to `/api/group-chat` (table `chat_reads`, migration 0005, also created on first use); polls return other members' read marks and your latest message shows Sent / Seen / Seen by. A thin bar attached under the chat button shows "x players online" with a green dot and opens the Online tab; signed-out visitors get the number from the public `GET /api/group-chat?count`. Invites: `meta.invite` {module,label,code}. Embedded modules with online rooms (sandlot, chess, checkers, shorttrack) answer `postMessage({type:'tl-host'})` with `{type:'tl-room', code}` and auto-join from `?room=`. No popups or sounds: while anything is unread the chat button flashes between pink and the accent color and the browser tab icon blinks a red dot (`apps/platform/src/lib/use-blinking-favicon.ts`), even with reduced motion on, until the messages are read.
- Themes: midnight / slate (label Gray) / light. Hub, sidebar and chat colors come from `--lib-*` variables per theme in styles.css; old theme ids map to these in site-themes.ts.
- Record resets: each high-score board registers its currently selected tab with `useRecordResetTarget` (`packages/shared/src/components/AdminRecordReset.tsx`). Only the admin sees the reset button, rendered at the very bottom right of every page by `AdminRecordResetButton`; it clears just the selected board. Reset endpoints accept the admin session (the old reset password still works server-side).
