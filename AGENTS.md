# myWorkHelper

TanStack Start / React 19 site on Cloudflare Workers with four areas: a creative studio (AI chat, images, lyrics), an 8-ball/9-ball pool game, a racing game with two tracks, Thrill Park (an original 3D theme-park builder), and accounts/admin. Live multiplayer for pool, racing and Thrill Park runs on a separate Node service in `server/` (Railway). The initial route must render this product, never a starter demo.

## File map

### Shell and shared UI
- `src/routes/__root.tsx`: document shell, metadata, favicon.
- `src/routes/index.tsx`: navigation, studio tabs (chat, image, lyrics), saved lyric styles, theme picker; mounts pool, account, admin, and lazy-loads racing.
- `src/styles.css`: all styling, CSS tokens, site themes, responsive layouts, reduced-motion and focus states.
- `src/lib/site-themes.ts`: site theme list. `public/`: favicon and images.

### Worker backend (`src/server.ts`, `src/server/`)
- `src/server.ts`: Worker entry. `/api/*` goes to `src/server/api.ts`; everything else to TanStack Start.
- `src/server/api.ts`: route table and error handling.
- `src/server/auth.ts`: PIN hashing (PBKDF2), sessions (`tl_session` cookie), lockouts, admin constant.
- `src/server/routes/account.ts`: `/api/pool-account` (login, logout, multiplayer tickets, ticket redeem), `/api/workspace-access`, `/api/account-settings`, `/api/workspace-admin`.
- `src/server/routes/pool.ts`: `/api/pool-practice`, `/api/pool-preferences`, `/api/pool-cue-overlay`.
- `src/server/routes/racing.ts`: `/api/racing` tickets, lap records, paint profiles, AI skins.
- `src/server/routes/fairway.ts`: `/api/fairway`, the Fairway Nine record book in D1 `fairway_records` (migration 0018, also created on first use). GET `?board=round|pin|match` (public) returns the top 20 ascending by value then date, plus the signed-in user's best; POST `record` (signed in, same-origin, Zod, `ON CONFLICT(id) DO NOTHING` on `<user>:<run>`) and `reset-records` (admin). Values: gross strokes (round), centimetres to the pin (pin), finishing place (match).
- `src/server/routes/rackreel.ts` + `src/server/rackreel.ts`: `/api/rackreel`, Rack & Reel saved progress in D1 `rackreel_profiles` (migration 0026, also created on first use): one JSON profile per user (cash, owned items, loadout, three active tasks, lifetime stats). GET returns the signed-in profile (`{signedIn:false}` otherwise). POST (signed in, same-origin, Zod): `fish` / `game` (species, value, legendary, boat / doe and stand; the server rejects impossible sizes, pays from `modules-src/rackreel/shared/Economy.ts` with a per-account cooldown and advances tasks), `tick` (time outdoors, at most two minutes since the last save), `buy` and `equip` against the shared catalog. Guests play with an in-memory profile only. High scores work like the site's other record books: D1 `rackreel_records` (migration 0030, also created on first use) holds one row per category for every accepted catch that reaches that category's top 20 (`BOARD_LIMIT`), keyed `<user>:<catch>:<category>`, with `detail` JSON (size class and all the animal's measurements). Categories are in `modules-src/rackreel/shared/Records.ts` (fish heaviest and longest; buck antler score, inside spread, points and field-dressed weight; bear weight and skull); the real Wisconsin marks there are shown only as a reference. An accepted (off-cooldown) `fish` or buck/bear `game` POST carries the animal's `seed`, and the server works out every measurement itself from species, size and seed (`measure` in `LootTableManager.ts`, deterministic, so shooter, online guests and server agree), writes each placing row through `saveWithKnockouts` (game `rackreel`, so knocked-out players get the usual notice) and replies with the in-game top three (`records`) and `placed`; it also derives `legendary` from `classify` instead of trusting the browser. GET `?records=1` (top three of every category, for the module) and `?board=<category>` (top 20 plus the viewer's best, for `src/components/RackReelRecordBoard.tsx` under the module frame, which refreshes on the module's `{type:'tl-rackreel', species}` message) are public; POST `reset-records` (admin, optional `category`) clears a board and is the board's admin reset target. POST `create-character` `{look}` (only the cosmetic `CHARACTER_CHOICES`, once) gives and wears the outfit and sets the profile's `verified`, which every profile, old saves included, starts without; the module shows its character creator (`ui/CharacterCreator.ts`) on Head out until the profile is verified. Guests' catches only go on this tab's copy of the board, and guests make a character each visit.
- `src/server/routes/angler.ts` + `src/server/angler.ts`: `/api/angler`, Northwoods Angler. Tables `angler_profiles` (one JSON profile per user: Tackle Credits, owned gear, look, boat paint, stats, achievements), `angler_sessions` (the anchored session: lake, spot, rig, next bite time, last seen) and `angler_catches` (every landed or lost fish; weight in tenths of an ounce, length in quarter inches) — migration 0020, also created on first use. GET `?board=<species>&lake=<id|all>&period=all|month` and `?hall=1` (the three heaviest of every species with when they were caught; what both record books show) are public; GET with no params returns the signed-in profile and recent catches. POST (signed in, same-origin, Zod): `start` (anchor at x/z with a rig; the server schedules the next bite on its own clock), `tick` (heartbeat with play-time and miles; when the bite is due and the angler was seen in the last 150 s the server rolls the catch with `crypto.getRandomValues`, writes it, pays credits and achievements), `stop`, `buy`, `equip`, admin `reset-records` and `void-catch`. At most one bite per 45 s per account; closed tabs earn nothing. `/api/angler-lake` (`src/server/routes/angler-lake.ts`) upgrades to the Durable Object `AnglerLake` (`src/server/angler-lake.ts`, binding `ANGLER_LAKE`, one per lake instance `<lake>:<0-7>`, 4 boats each, 8 connections): shared lakes with other anglers' boats, crews of two on one boat, and catch news. It stores nothing; catches still come only from `/api/angler`, which passes the instance (`room`) so the DO can announce landed fish and confirm crews for the Boat Party achievement.
- `src/server/routes/darts-records.ts` + `src/server/darts-records.ts`: `/api/darts-records`, the Darts record book, one per board (`steel`, `spider`) and format (`501`, `301`, `cricket`, `countup`; rules in `modules-src/darts/shared/Records.ts`). D1 `darts_legs` and `darts_matches` log every saved leg and match once (`<user>:<run>`), `darts_bests` keeps each player's best with `times` (how often they hit it; ties sort by more times, then who set it first) and `darts_averages` their running darts and points/marks (migration 0031, also created on first use). GET `?board=&mode=` (public) returns the bests, the top five all-time averages (PPD for 301/501, MPR for Cricket, from 30 darts) and the signed-in player's own; `&players=a,b` returns those players' totals. POST (signed in, same-origin, Zod) `leg` and `average` from the page for local play, admin `reset-records`; online rooms save their members' results from the Durable Object.
- `src/server/routes/darts.ts` + `src/server/darts-room.ts`: `/api/darts`, Darts online rooms. GET `?room=<code>` says whether a room is open, full or playing; a same-origin WebSocket upgrade with `mode=create|join` (members by session, guests by a zod-checked key) takes a seat in the Durable Object `DartsRoom` (binding `DARTS_ROOM`, one per `room:<code>`, up to four seats, nothing stored). The room is the authority: THROW_MADE carries only the aim, speed, yaw and steadiness; the room rolls the release error with `crypto.getRandomValues`, flies and scores the dart with `modules-src/darts/shared/` and broadcasts THROW_MADE, TURN_SWITCH and GAME_OVER (45 s turn timeout, 90 s seat hold), and saves signed-in players' finished legs and match averages to the record book. RESTART_REQUEST is the pause menu's Request Restart: the room restarts the match once every connected player has asked (RESTART_VOTES; votes lapse after 30 s).
- `src/server/routes/park.ts`: `/api/park` multiplayer tickets (prefix `park:`), ticket redeem, gzip-compressed saves, one per park in `park_saves_by_park` keyed by user and `parkId` (`src/server/park-saves.ts`, created on first use; the server reads the park from the save data). Saving, the 5-minute autosave and leaving all write that park's own save and never touch another park; a park leaves the account and the leaderboard only through `delete`. The one-time `one-save-per-park` migration (`park_migrations`) moved the old slot saves (`park_saves`) and older `park_scores` leaderboard rows across; both old tables are kept but no longer read, and per-map company-value leaderboards in `park_scores_by_park` (one row per named park, keyed by `parkId`; it and `park_scoreboard_resets` are created on first use, plus `shot_at`, migration 0012). After every save and autosave of a solo scored park, the HUD posts `score` with `companyValue` (park value + cash − loans), the park name and the save as `snapshot`, then renders a whole-park overview with `ParkRenderer.captureOverview` (owned land framed at midday, JPEG) and posts it as `shot`, stored in KV `park-shot/<parkId>` and served publicly at `?shot=<parkId>`. Parks carry `named`; the HUD blocks play with a naming dialog until the player names the park (the `park` command sets `named`). The board's View button opens `ParkShotDialog.tsx` with the screenshot for anyone, signed in or not; from the menu board it also offers "Walk around in 3D" (`?view=<scenario>&park=<parkId>` returns the snapshot, opened read-only through `ViewSession`). Below each map's Richest Parks table is the Million Dollar Dash: the quickest in-game time (`time.seconds`) to `MILLION_VALUE` ($1,000,000 park value, `parkValue`) with a `MILLION_RATING` (750) rating at the same moment. The sim records the first such moment once in `park.millionAt` (`checkMillionDash` in `sim.mjs`, run with the rating update; older saves are backfilled from complete monthly history by `millionFromHistory`, flagged `approx`), saves keep it, and the server reads it from the snapshot sent with `score` into `park_million_by_park` (one row per park, fastest time kept, created on first use, removed on `delete`). `reset-scores` clears both boards for the map. Admin `reset-scores`. The board is `src/components/park/ParkScoreboard.tsx`.
- `src/server/routes/hood.ts` + `src/server/hood.ts` + `src/server/hood-lot.ts`: `/api/hood`, The Hood. - `src/server/routes/maplestreet-items.ts`: `/api/maplestreet-items`, Fox Plains's admin item pipeline. PATCH (admin, JSON `{id, status?, active?, name?, price?}`) publishes a draft, retires or restores an item. POST (admin, multipart: `model`, optional `wheel`, `name`, `spec` JSON checked by Zod `vehicleSpecSchema` in `src/server/maplestreet-vehicles.ts`) stores the record in D1 `maplestreet_assets` (kind `vehicle`) and, when published, refreshes the `MapleStreetWorld` catalog; optional `status` `draft`/`published`. - `src/server/routes/shorttrack-cars.ts` + `src/server/shorttrack-cars.ts`: `/api/shorttrack-cars`, admin-made Short Track Showdown bodies. Rows in D1 `maplestreet_assets` with kind `stcar` (spec checked by Zod `carSpecSchema`, types in `modules-src/shorttrack/shared/CustomCars.ts`), models in KV `shorttrack-car/<id>`. GET lists published and retired cars (public; drafts only to the admin with `?drafts=1`); `?model=<id>&v=<version>` serves the .glb with an immutable cache. POST (admin, multipart: `name`, `spec`, optional `model` (.glb), `status` `draft`/`published`, optional `id` to save over a car); PATCH `{id, status?, name?, spec?}` publishes, retires or restores (never back to draft). Every custom car drives on the stock Super Late Model's physics; the spec places the model, sizes the wheels, picks the part that takes the driver's paint (`body`, the default, paints the whole model; `none` from older saves now means `body`), sets `garage` (which Garage options drivers get: `schemes`, `logos`, `numbers`; the main color is always theirs; missing means all) and the door, roof and tail number spots and brake lights. `modules-src/shorttrack/shared/carRepaint.ts` puts the full Garage livery on any body: the livery is drawn in the stock car's atlas as two layers (base paint and decals: logos, lettering, painted-on numbers) and every texel of the body is painted from its own 3D point by `modules-src/shorttrack/shared/liveryWrap.ts`: base paint follows the smooth normal with a narrow, side-biased blend so side and top/end art meet along clean lines instead of jagged face edges, decals are projected onto every outer texel facing them so a logo runs over a seam in one piece, and `fitDecal` moves (and if needed shrinks) side logos and door numbers onto painted panel, off wheel openings and windows, using the body's own projection maps (`customGeo`; wheels added as discs). The stock car gets the same treatment (`carLiveryTex` with `stockGeo`/`stockPlan`: seam texels planned once at 1024, upsampled for the crisp 2048 livery). `paintShade` keeps glass and tyres dark and flattens blotchy generated textures; where a model's UVs overlap the outer surface wins; numbers are decals at placed spots and painted on at the stock spots otherwise. This needs nothing from the admin: every body uploaded later is mapped from its own geometry. Windows and the rear spoiler never take paint: `modules-src/shorttrack/shared/carClear.ts` finds them on textured custom bodies (windshield, rear window between the sail panels, spoiler plate above the deck) and `custom-cars.js` draws them as tinted see-through glass and clear Lexan; the stock Super Late Model's glass is see-through and its spoiler is split into its own Lexan material.

GET `?field=1` is public (`{designs}`, plus `info` with the notes for the admin); the page loads it into `FIELD_DESIGNS`, and `schemeOf`/`cleanLv` paint an AI car from its design (colours and number colours too) instead of `ICONIC`, so every driver sees the same field. ### Learning modules
- Site-facing copy calls everything "Learning Modules" on a site named "the library" (always lowercase). Never use the words game(s), gaming or entertainment in visible text, titles or metadata.
- `src/lib/modules.ts`: module catalog (titles, subjects, thumbnails in `public/images/modules/`). `src/components/ModuleHub.tsx`: the homepage library.
- Learning-module pages are built from `modules-src/<id>/` (`index.html` + `index.ts`, plus `main.js` for the older single-file modules) into `public/modules/<id>.html` and hashed chunks in `public/modules/chunks/` by `vite.modules.ts`, which `vite.config.ts` runs as part of `pnpm build` and `pnpm dev`. The generated files are git-ignored. - Thrill Park (`#park`, module id `park`): `server/park/` is the shared simulation (terrain, catalog, coaster track physics, commands, guest and staff AI, finances, snapshots; types in `index.d.mts`). `src/lib/park/` holds the dependency-free WebGL2 renderer (`gl.ts`: smooth-normal mesh builder with per-vertex materials (`materials.ts`) and baked AO, indexed 24-byte vertices, GGX lighting with ACES tonemap, fitted sun shadow map with rotated PCF, height fog, procedural ground and water shading; quality tiers `low`/`medium`/`high` in `quality.ts` (`?quality=`, HUD button; `captureOverview` always renders `high`); `models.ts`: guests built by `addPerson` with 8 walk frames plus idle, 8 looks and a near/far detail level, organic scenery; `renderer.ts`: blended terrain with ambient occlusion and shorelines, built in `CHUNK` (16×16-tile) pieces that re-mesh only when a tile within `CHUNK_MARGIN` of them changes, and coaster track meshes that rebuild only when the ground, paths, scenery or track under them change (`trackSiteKey`), so placing something never rebuilds the whole park, a shadow pass then the main pass via `drawWorld`), the local and online sessions (`session.ts`) and the saves client (`api.ts`). The guest cap (`spawnRate` in `sim.mjs`) is the smallest of 4 × (30 + rideScore·26 + stalls·8), owned land × `GUESTS_PER_OWNED_TILE` (0.7, counted by `ownedTileCount` in `land.mjs`, cached by `state.landVersion`) and `MAX_GUESTS` (6,400 per park); `p.spawn.limit` says which applies and `GuestCapacity.tsx` shows it. Slopes rise `SLOPE_RISE` (0.5 m), half of `STAIR_RISE` (1 m). A raised path tile stores its high end and ramps down to its lower neighbour (`pathRamp` in `terrain.mjs`; footpaths, queues and boardwalks ramp at most one slope, stairs any height), so sloped pieces run straight and a climb never directly follows a descent. Path geometry (ramps, stepped stairs, deck fascia, railings, legs) is `src/lib/park/pathModels.ts`, shared by built paths and the ghost. Every path tile stores its placement number in `map.pathOrder` (set by the `path` command from the drag's start, saved like the other map arrays, 0 in older saves), and queue lines follow that order (`server/park/queues.mjs`: `queueLinks`, `queueStep`, `queueLayout`): `followLine` walks from the ride gate along the build order, so a line that weaves row on top of row keeps its rows, and the renderer rails every queue tile on both sides (one railing per shared edge, always, not only when raised), runs the two stripes the way the line runs with a right-angle bend where it switches lanes, and leaves openings only at the gate end and where the line meets the footpath (`line.entry`→`join`; an unfinished line opens straight ahead of its last-laid tile). Auto-finish is the `pathFinish` command (`exit`, `sloped`), which searches down to the ground or an existing path and builds nothing if it can't. A level boardwalk piece is a flat deck on the tile's highest corner (or just above water) plus whole half-metres, never ground-following: the builder plans it that way (`planBoardwalk`), holding the run's height on stilts where the ground falls away and stepping up where it rises, and checks every planned piece against the `path` command's side-neighbour step rule (`stepsTooHigh`) so the ghost shows any refusal first. Ride exits can use queue-line tiles: `exitLine` in `guests.mjs` follows them to the footpath and guests walk out along it (`exitRide`/`exitStep`); entrance `queueLine`s never route through exit-line tiles. ## Conventions

Use TypeScript, descriptive identifiers, React hooks, and type-only imports. Keep provider SDKs and database imports out of client modules. Server and database relative imports use `.js` extensions. Validate runtime input with Zod. Preserve the CSS token system, responsive layouts, reduced-motion support, keyboard accessibility, and loading, empty, and error states. Do not add inline comments unless requested. Prefer adding new modules over growing the already large files.

## Platform rules

- All AI runs server-side. The studios (AI chat, Image Studio, Lyric Studio) run on Claude with the `ANTHROPIC_API_KEY` Worker secret: chat and lyrics are written by Claude, and every image request is vetted and turned into a render instruction by Claude (which also sees the source picture for edits) before Gemini draws the pixels, because Claude models do not output images. Studios never accept or produce code (see `src/server/code-guard.ts`); each studio is only for what its name says. The rest of the site uses Gemini with the Gemini API key secret, and Meshy 3D generation (admin only) with `MESHY_API_KEY`. Text uses `gemini-3-flash-preview`; images use `gemini-3.1-flash-image`; songs use Lyria (`lyria-3.5`, `lyria-3-clip-preview`). Song Maker exception: its free mode needs no key; `public/modules/songmaker-synth.js` builds the instrumental in the browser with Web Audio, and `write` falls back to the keyless Pollinations text API, then to the offline template writer in `src/server/keyless-lyrics.ts`. Never expose environment values or provider errors.
- Use D1 for structured records and KV for binary data. Never use local files, browser storage, or in-memory persistence for data that must persist.
- Schema changes go in a new numbered file in `migrations/` and are applied with `wrangler d1 migrations apply thelibrary-db --remote`.
- Non-GET endpoints check same origin. Ticket redeem endpoints are server-to-server and skip it.

## Accounts and access

- Accounts are a username (3–20 letters, numbers, `_`, `-`, stored lowercase) and a password of 3 or more characters (up to 128), hashed with a per-user salt. Older accounts created with 3 digits keep working. No registration page, email or recovery: an unknown username creates the account; a known username with the wrong digits returns "Invalid password."
- Wrong passwords lock the username after 5 attempts (15 minutes, doubling each time up to 24 hours) and the network after 25. Each network can create 10 accounts per day.
- The administrator is `stoegbauer`, whose password is the `ADMIN_PASSWORD` secret . The admin can rename accounts, grant studio pages, reset a password (next sign-in sets the new password) and delete accounts.
- Studio pages (chat, image, lyrics) require a grant from the admin. Pool and Racing require sign-in for saved data.
- Pool appearance, cue overlay, racing paint, lobby sound, site theme, saved lyric styles and lyric corrections are stored per account. There is no creation library; creations are kept only so revisions and version history work. Never include `user_id` in API responses.

## Studio rules

- Never claim chat includes live browsing or personal document retrieval.
- No code in any studio: chat, images and lyrics refuse requests for code, scripts, commands or markup, reject inputs that contain code, and discard any output that looks like code. Each studio stays on its own purpose (chat converses, Image Studio makes and edits pictures, Lyric Studio writes lyrics).
- Lyrics are written in plain, literal, logical everyday language: no metaphors, similes, personification, invented phrases or forced rhymes; only common expressions people really say. `songwriterInstruction` holds these rules and `clichesIn` triggers one rewrite when stock phrasing slips through.
- New lyrics, fine-tunes (`revise`), full rewrites (`revamp`), and manual edits are distinct. Fine-tunes are surgical, accumulate in `tuning`, and keep untouched lines. Revamps rewrite every line with current settings and keep the topic. Every derived version stores `parent_id`.
- Saved lyric styles store the full song settings including `instructions`, the user's standing writing directions, which the model follows as preferences under the mandatory rules.
- Explicit mode (default on) allows profanity but never slurs against protected groups.
- Artist influence and custom genres are researched server-side and cached in `research`, which is never public.
- Prompt text and instructions are ideas only: lyrics copying 4–5 word runs are regenerated once, then rejected. The validator requires bracketed sections and forbids intro lyrics.
- Image downloads are re-encoded through canvas. Serve stored images only through the ownership-checked `/api/asset`.

## Games rules

- `server/racing-engine.mjs` is shared by browser and server. Any change to it, or to server lobby/race code, requires redeploying the multiplayer service; bump the `/version` string in `server/index.mjs` and note it in `server/README.md`.
- Keep single-player and multiplayer physics identical by changing the shared engine rather than duplicating logic in `Racing.tsx`.
- Lap records are stored per track and mode. Short Track Showdown (`modules-src/shorttrack/`, served as `public/modules/shorttrack.html`) posts to `/api/racing` with track `shorttrack` (Showdown Bullring), `dells` (Dells Short Track), `dellswide` (Dells Wide Oval: the Dells layout 8° flatter, 30 m turn radius, 10% wider, bare grass infield with no pit road, garages, haulers or pylon via `bareInfield`), `prison` (Prison Speedway: a blend of the three asphalt layouts with more grip for every car, `theme:'prison'` adds the castle-style stone guard towers, crenellated curtain wall, razor wire, night searchlights and orange-clad inmate crowd from `modules-src/shorttrack/prison-speedway.js`) or `dirt` (Dells Dirt Oval, dirt handling; picked in the module menu via `?track=`, which defaults to `prison`, listed first; the walled infield cell house comes from `buildPrisonInfield`; day or night is a switch on the track picker, `#sNight`, carried through the track reload as `?night=1`) and modes `time-attack`, `race` (shown as Solo Race) and `multiplayer`; races start with a half-lap rolling start from the back stretch, two wide with a car length between rows (`GRID_S`, `GRID_ROW`); the AI drives every car, the player's included (`c.auto`), in a rigid formation at `FORM_V` (the slowest centerline speed both files can hold through the turns, at most `CFG.aiPaceSpeed`) until the leader takes the green at the line, then the player takes over; `AI_LEVELS` sets AI corner skill, braking, passing reach and aggression, while traffic awareness is the same at every level (path scan for the car ahead with a stopping-distance speed limit, `laneClear` sweeping the whole lane change, `passLane` picking the inside or outside, wreck avoidance via `isHazard`, lifting near the wall, catching slides, and a bump-and-run when held up: `bumpT` closes at a tap, and a tapped AI gets loose for `looseT`; lateral margins come from `AI_TOUCH`/`AI_GAP`/`AI_PASS`, lane changes move at `AI_SHIFT` m/s through `relLane`, turn speed is capped at `AI_CORNER` of the real grip limit, and the two files hold their lanes off the green for `startHoldT` via `startLane`; dirt uses wider margins); Time Attack is never stored in `settings`, so a race after a Time Attack session still gets the rolling grid; the in-race HUD shows the running order, and only Time Attack shows the track's top 20 laps and lap-record popups (race laps are still saved to the site board), AI cars come from `AI_FIELD`, built from `ICONIC_FIELD` in `modules-src/shorttrack/iconic-schemes.js`: each AI number runs a look-alike of the iconic NASCAR scheme that number is known for (parody driver names, knockoff logos in `LOGOS`, no real trademarks), named by `lv.scheme` (kept by `cleanLv`) and painted by `drawSchemeSide`/`drawSchemeHood` on the truck decals (`tmSideTex`, `tmHoodTex`) and the stock-car atlas (`carLiveryTex`); numbers are unique, and an AI car whose number a human is running sits out rather than being renumbered; a random subset of the field starts each race and the whole grid, humans included, is shuffled in `hostStart`; AI pace: `aiBaseline()` averages the track's top 20 Time Attack laps (fetched on load, public), each AI gets a lap target `tl` = baseline x `AI_LEVELS[diff].pace` (hard 1.0, medium 1.025, easy 1.05) +/- `vary`, and `aiPace` measures rolling laps at the line and half distance to trim `c.paceK` toward it (above 1 it adds corner speed, power and grip; below 1 it takes mostly power via `aiCornerK`/`aiPaceApply`, so the AI keeps its corner speed); AI turn speed runs at `AI_CORNER` 0.998 of the real grip limit (0.975 on dirt) with a grip edge `gb` of 1.065/1.085/1.105 (easy/medium/hard); with fewer than 3 record laps the AI runs its raw level; car-to-car rebound and contact yaw kick are scaled by `CFG.carBounce` (0.7); in the turns the AI lifts instead of braking (`brkAt` 5 m/s over target) unless `brkTight` (a wreck within 35 m or a car it is about to hit), and its turn-entry target rises from the entry speed to the mid-corner speed over the first fifth of the turn, so a driver following closely is not brake-checked; every completed lap by the signed-in driver is sent (every time attack lap, and every race lap until that driver takes the checkered flag), and boards list every lap, so one driver can hold several places. The truck body is the owner's race-truck model (lofted body, greenhouse, roll cage, fascia, bed wing), embedded in the module as `TM` and scaled to the physics size; after the world and each truck are built, `batchStatic` (`modules-src/_shared/static-batch.js`) merges rigid parts per material (a 12-truck race went from about 4,800 to 1,240 draw calls per frame); anything that moves, deforms or is toggled on its own (wheel pivots, the deformable body and decals, sky, clouds) must stay out of it or be passed in `exclude`; liveries are conforming decal meshes on the sides, hood and roof. Race numbers come from `modules-src/shorttrack/shorttrack-numbers.js` (20 Google Fonts digit subsets, 11 styles plus slant, size 60–150% with 125% default, fill/outline/accent colors) and sit on their own decals on the doors, roof and tailgate; `cleanLv` keeps older liveries and older peers working (`italic` becomes `block` plus slant). Drivers pick a vehicle on the track screen or in the garage, stored as `veh` in the livery (`truck` or `car`): the car is a plain super late model loaded from `public/modules/shorttrack-car.bin` (decimated from the owner's model with its original graphics removed), built by `buildStockCar`. Its paint faces carry atlas UVs (side, roof, rear and front regions listed in the file's `regions`), and `carLiveryTex` paints the livery pattern and race numbers into one texture in world metres (`CAR_NUM_SPOTS` sets the door, roof and tail number spots). It uses the truck's scale, physics and dimensions. AI fields use the host's choice; the pace vehicle stays a truck. `src/components/LapRecordBoard.tsx` shows the all-time top 20 per mode (tabs) under each racing module page: Max Secure Circuit and Oval Speedway via `Racing.tsx`, Short Track Showdown under its iframe. Short Track's board uses the `-v2` keys with the classic books under its Classic tab (`archive` prop). `GET /api/racing?records` is public; the module posts `{type:'tl-lap',track}` to the parent after a saved lap so the board refreshes.
- Bush League Baseball's `modules-src/bushleague/sim/` is the single authority for its rules: change rules there, never in `systems/` or `ui/`, and keep the replay test green (`tests/rules.test.ts`, determinism cases).
- `server/park/` is shared by browser and server in the same way: change park rules there, never in the UI, and redeploy the multiplayer service afterwards. ## Development

Read docs/ENGINE-MAP.md before changing any module; keep it current. The shared 3D engine is `engine/` (barrel `engine/index.ts`); a new 3D module starts as a copy of `modules-src/_template/` renamed without the `_`, and `pnpm engine:smoke` checks the template in a hub-like iframe.

Install with `pnpm install`; develop with `pnpm dev`. Everything `pnpm build` and the deploy command need (Vite and its plugins, esbuild, sharp, wrangler) is in `dependencies`, not `devDependencies`, because Workers Builds installs with `NODE_ENV=production` and skips devDependencies; keep it that way when adding build tooling. `pnpm build` runs Vite with a 6 GB Node heap (`--max-old-space-size=6144`) as headroom on Workers Builds' 8 GB machines. Import Babylon.js by path (`@babylonjs/core/Engines/engine` and so on), never from `@babylonjs/core` itself: the package root pulls in the whole library and every shader (about 3,150 modules, a 7 MB chunk), which pushed the build past Node's default heap of about 2 GB; imported by path, the build fits in that default. Every change reaches `main` through a pull request: the `modules` workflow (`.github/workflows/modules.yml`) runs `pnpm assets:check`, `pnpm build` and `pnpm test`, and `main` requires it. `pnpm gate` (`scripts/module-gate.mjs`) loads every embedded module in the hub iframe with Playwright and reports console errors and screenshots. The 3D code index is `docs/ENGINE-MAP.md`; update it whenever a file it lists changes. Pushes to `main` build and deploy automatically through Workers Builds. When Workers Builds can't deploy, the manual `Deploy site` workflow (`.github/workflows/deploy-site.yml`, Actions → Run workflow) builds `main` and runs `wrangler deploy` with the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets.

- Chat: floating `GroupChat` component (src/components/GroupChat.tsx) polls `/api/group-chat` (D1 `chat_messages` + `chat_presence`, migrations 0002–0003). `thread` NULL = everyone; otherwise the sorted comma list of member usernames (private chat, up to 8). Presence (who's online) comes from these polls, not Railway. Read receipts: viewing a thread posts `{action:'read', thread, id}` to `/api/group-chat` (table `chat_reads`, migration 0005, also created on first use); polls return other members' read marks and your latest message shows Sent / Seen / Seen by. A thin bar attached under the chat button shows "x players online" with a green dot and opens the Online tab; signed-out visitors get the number from the public `GET /api/group-chat?count`. Invites: `meta.invite` {module,label,code}. Embedded modules with online rooms (sandlot, chess, checkers, shorttrack, party, angler, bushleague, rackreel, pingpong, darts) answer `postMessage({type:'tl-host'})` with `{type:'tl-room', code}` and auto-join from `?room=`. No popups or sounds: while anything is unread the chat button flashes between pink and the accent color and the browser tab icon blinks a red dot (`src/lib/use-blinking-favicon.ts`), even with reduced motion on, until the messages are read.
- Themes: midnight / slate (label Gray) / light. Hub, sidebar and chat colors come from `--lib-*` variables per theme in styles.css; old theme ids map to these in site-themes.ts.
- Record resets: each high-score board registers its currently selected tab with `useRecordResetTarget` (`src/components/AdminRecordReset.tsx`). Only the admin sees the reset button, rendered at the very bottom right of every page by `AdminRecordResetButton`; it clears just the selected board. Reset endpoints accept the admin session (the old reset password still works server-side).
